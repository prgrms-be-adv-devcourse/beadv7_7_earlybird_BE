Modernize and refactor this codebase.

Requirements:

- Apply a DDD layered-architecture lens (Presentation / Application / Domain / Infrastructure) with strict attention to dependency direction: dependencies must point inward toward Domain, and Domain must have zero knowledge of Infrastructure or Presentation. Identify violations such as: domain models coupled to ORM/framework annotations, domain or application code importing concrete infrastructure implementations instead of depending on interfaces/ports defined in the domain layer, application logic depending on presentation-layer DTOs or controllers, layer-skipping calls (e.g., presentation calling infrastructure directly), and circular dependencies between internal modules or bounded contexts.

- Score these passes using the same risk rules above — dependency-direction fixes that don't change method signatures or call sites are typically low risk; ones that require introducing new interfaces used across many callers are medium-to-high risk depending on blast radius.

- Before proposing refactor passes, assess whether existing tests are trustworthy for the target modules: check coverage scoped specifically to the files being touched (not aggregate repo-wide coverage), flag tests that assert implementation details (heavy mocking, call-count checks) versus tests that assert actual input/output behavior, and note any modules where test confidence is low. - Start by identifying dead code, duplicated paths, oversized modules, stale abstractions, and legacy patterns that are slowing changes down.
- Order the proposed passes from lowest risk to highest risk. Score risk using: (a) blast radius — how many call sites or modules depend on the code being touched, and whether it's part of a public API; (b) test confidence — as assessed above; (c) change type — deletions and renames are lowest risk, extracting helpers is medium, control-flow changes are higher, architecture moves are highest. State the risk level and its basis for each pass.
- For each proposed pass, name the current behavior, the structural improvement, and the validation check that should prove behavior stayed stable.
- If a validation check fails after a pass, do not immediately retry or immediately revert. First classify the failure: (a) a genuine behavior regression caused by the change, or (b) a false failure caused by a test that was asserting implementation details rather than behavior (per the test-trustworthiness assessment above). For (a), roll back the pass, state the root cause, and propose a revised approach before retrying. For (b), propose fixing or removing the flawed test as its own separate, reviewable change — do not fold that fix into the same commit as the refactor. Never mark a pass as complete while a validation check is failing.
- Break the work into small reviewable refactor passes such as deleting dead code, simplifying control flow, extracting helpers, or replacing outdated patterns with the repo's current conventions.
- Keep public APIs stable unless a change is required by the refactor.
- Call out any framework migration, dependency upgrade, API change, or architecture move that should be split into a separate migration task.
- If the work is broad, propose the docs, specs, and parity checks we should create before implementation.
