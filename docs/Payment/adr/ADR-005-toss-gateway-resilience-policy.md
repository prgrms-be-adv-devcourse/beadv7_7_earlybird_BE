# Payment-Service 기술 의사결정 요약 `#005`

- 날짜 : 2026-08-21

##  무슨 상황 인가요?

- 문제 상황: Toss 승인, 결제 조회, 환불 호출은 서로 다른 트래픽 특성과 장애 영향을 가집니다.
- 하나의 RateLimiter를 공유하면 승인·조회·환불 호출이 서로의 허용량을 소모해 정상 요청까지 차단할 수 있습니다.
- PG의 5xx, 타임아웃, 네트워크 장애는 일시적일 수 있지만, 금액 불일치 등 4xx 오류는 재시도해도 성공하지 않습니다.
- 승인·환불은 PG에서 이미 처리됐지만 응답을 받지 못할 수 있어, 모든 실패를 즉시 최종 실패로 처리할 수 없습니다.

## 무엇을 목표로 하나요?

- 목표 품질 속성 : 가용성, 장애 격리, 정합성
  - 승인·조회·환불 요청이 서로의 호출 한도를 침범하지 않아야 합니다.
  - 일시적 장애는 제한된 횟수만 재시도하고, 반복 장애 중에는 PG 호출을 빠르게 차단해야 합니다.
  - 재시도할 수 없는 오류에 불필요한 호출을 하지 않아야 합니다.
  - PG 처리 여부가 불명확한 실패는 결제·환불 복구 흐름으로 넘겨야 합니다.

## 무엇을 선택 했나요?

- 승인, 조회, 환불에 각각 독립된 `RateLimiter`를 둡니다.
  - 각 Limiter는 750ms당 1건을 허용하고 대기 없이 즉시 거절합니다.
- 각 호출은 `Circuit Breaker → Retry → RateLimiter → Toss 호출` 순서로 조합합니다.
  - Circuit Breaker는 Retry가 모두 소진된 최종 결과를 기록합니다.
  - Retry의 각 시도는 RateLimiter를 다시 통과해야 합니다.
- 승인과 환불은 최대 3회, 결제 조회는 최대 2회 재시도합니다. 재시도 간격은 1초입니다.
- Circuit Breaker는 최근 10건 중 최소 5건 이후 실패율 50% 이상이면 열고, 30초 뒤 half-open 상태에서 2건을 허용합니다.
- `UNCERTAIN` 실패만 Retry 및 Circuit Breaker 실패로 기록합니다.
  - 네트워크 연결 실패, 5xx, 408, 429, 응답 해석 실패, 처리 완료 여부를 확인할 수 없는 Toss 오류 코드는 `UNCERTAIN`입니다.
  - 금액·요청 값 불일치처럼 Toss가 처리하지 않았음이 확정된 오류는 `DEFINITIVE`입니다.
- `DEFINITIVE` 승인 실패는 Payment를 `FAILED`로 전이합니다. `UNCERTAIN` 승인 실패는 `CONFIRMING`을 유지해 복구 배치가 Toss 상태를 조회합니다.
- 환불도 동일한 분류를 사용하며, `UNCERTAIN` 실패는 환불 재시도·복구 대상으로 남깁니다.

```text
승인 / 조회 / 환불별 독립 RateLimiter
                |
Circuit Breaker → Retry → RateLimiter → Toss API
                |
       DEFINITIVE / UNCERTAIN 분류
          |                    |
      즉시 최종 처리       재시도 또는 복구 배치
```

- 희생/비용 :
  - 호출 유형별 Resilience4j 인스턴스와 설정값을 관리해야 합니다.
  - Retry가 RateLimiter 허용량을 사용하므로 장애 시 요청 완료까지 지연될 수 있습니다.
  - `UNCERTAIN` 실패는 즉시 종결하지 않아 복구 주기만큼 결제·환불 상태 확정이 늦어질 수 있습니다.

## 선택의 근거는 어떻게 되나요?

- 승인·조회·환불의 호출 한도를 분리하면 조회 트래픽 증가가 승인 또는 환불 가능 여부에 영향을 주지 않습니다.
- RateLimiter를 Retry 안쪽에 두면 재시도 폭주도 Toss 허용량 안에서 제어할 수 있습니다.
- Circuit Breaker가 Retry 최종 결과만 기록하므로, 한 사용자 요청의 개별 재시도 실패가 장애율을 과도하게 부풀리지 않습니다.
- 확정 실패와 처리 결과 불명을 나누면 이미 PG에서 처리된 결제·환불을 잘못 실패 처리하는 일을 줄일 수 있습니다.
- Retry, Circuit Breaker 모두 `UNCERTAIN` 예외에만 반응하므로 입력 오류나 정책 위반으로 PG를 반복 호출하지 않습니다.

## 선택지의 한계는 무엇인가요?

- RateLimiter는 현재 단일 인스턴스 메모리 기반이므로, 다중 인스턴스 환경에서는 전체 서비스 기준 Toss 호출량을 제한하지 못합니다.
- 750ms당 1건이라는 값은 현재 운영 가정이며, 실제 Toss 한도와 부하 측정 결과에 따라 조정이 필요합니다.
- HTTP 상태와 Toss 오류 코드만으로 처리 결과를 완벽히 판단할 수 없으므로, `UNCERTAIN` 분류와 복구 배치가 계속 필요합니다.
- Kafka 발행이나 Order 상태 반영 장애는 이 정책의 범위가 아니며 Outbox·소비자 멱등성 정책으로 처리합니다.

## 다른 선택지는 무엇이 있었나요?

- 기타 선택지 1 : 모든 Toss 호출이 하나의 RateLimiter를 공유합니다.
  - 설정은 단순하지만 조회 부하가 승인·환불 호출을 차단할 수 있습니다.
- 기타 선택지 2 : 모든 예외를 같은 횟수로 재시도합니다.
  - 구현은 단순하지만 확정 실패를 반복 호출하고, 이미 처리됐을 수 있는 요청의 상태 정합성도 보장하지 못합니다.
- 기타 선택지 3 : Circuit Breaker 없이 Retry만 사용합니다.
  - 단기 장애는 완화할 수 있지만 PG가 장시간 장애일 때 요청마다 재시도를 반복해 요청 스레드와 PG 부하를 늘립니다.
- 기타 선택지 4: Payment/Refund Gateway의 Resilience4j 실행·예외 변환 로직을 공통 컴포넌트(또는 상위 클래스)로 추출합니다.
  - PaymentGatewayException/RefundGatewayException, 실패 타입 판정 조건(Toss 오류 코드)이 도메인마다 달라 공통 인터페이스로 묶으면 오히려 각 도메인 정책을 제네릭 타입 뒤로 숨기게 됩니다. Refund Gateway는 현재 실행 경로가 하나뿐이라 클래스 내부 중복도 없어, 추상화 비용 대비 이득이 낮다고 판단해 채택하지 않았습니다.
