# Payment-Service 기술 의사결정 요약 `#004`

- 날짜 : 2026-08-21

##  무슨 상황 인가요?

- 문제 상황: Toss 승인 API는 네트워크 호출이므로 응답 지연, 타임아웃, 응답 유실이 발생할 수 있습니다.
- DB 트랜잭션을 유지한 채 Toss 승인 API를 호출하면 커넥션과 행 잠금을 오래 점유합니다.
- 승인 요청의 결과가 불명확한 경우, Toss에서는 이미 승인됐지만 Payment가 응답을 받지 못했을 수 있습니다.
- 동일 결제의 동시 승인 요청은 PG 중복 호출과 상태 덮어쓰기로 이어질 수 있습니다.

## 무엇을 목표로 하나요?

- 목표 품질 속성 : 정합성, 가용성, 동시성 안전성
  - 외부 PG 호출 동안 DB 트랜잭션을 유지하지 않아야 합니다.
  - 한 결제에 대한 승인 처리 권한은 한 요청만 가져야 합니다.
  - 확정 실패와 처리 결과 불명 실패를 구분해야 합니다.
  - 결과 불명 결제는 PG 상태를 재조회해 최종 상태로 정합화할 수 있어야 합니다.

## 무엇을 선택 했나요?

- 승인 흐름을 `PaymentApprovalSagaOrchestrator`와 `PaymentConfirmationService`로 분리합니다.
- 첫 트랜잭션에서 `READY → CONFIRMING`으로 상태를 전이하고, 승인 멱등 키·금액·PG 주문 번호를 반환한 뒤 커밋합니다.
- 커밋 이후 Toss 승인 API를 호출합니다. 이 구간에는 DB 트랜잭션을 유지하지 않습니다.
- 승인 성공 시 새 트랜잭션에서 PG 응답의 paymentKey·주문 번호·금액을 검증하고 `PAID`로 전이합니다.
- Toss가 확정 거절을 반환하면 `FAILED`로 전이합니다. 타임아웃·네트워크·5xx처럼 처리 결과가 불명인 경우는 `CONFIRMING`을 유지합니다.
- `@Version` 기반 낙관적 락 충돌은 `PaymentConfirmationInProgressException`으로 변환해 두 번째 승인 요청을 거절합니다.
- 일정 시간 이상 `CONFIRMING` 상태인 결제는 복구 배치가 Toss 상태를 조회합니다. 조회 결과에 따라 `PAID` 또는 `FAILED`로 정합화하고, 계속 처리 중이면 최대 CONFIRMING 허용 시간을 기준으로 실패 처리합니다.

```text
READY
  |
  | startConfirmation() 트랜잭션
  v
CONFIRMING -- commit --> Toss 승인 호출 (트랜잭션 없음)
  |                              |
  | 성공                         | 확정 실패
  v                              v
PAID                           FAILED
  ^
  |
  +-- 결과 불명: 복구 배치가 Toss 상태 조회 후 정합화
```

- 희생/비용 :
  - 승인 처리 중 `CONFIRMING`이라는 중간 상태와 복구 배치가 필요합니다.
  - 승인 요청은 동기 응답을 즉시 보장하지 못하며, 결과 불명 시 복구까지 기다려야 합니다.
  - 승인 Saga와 상태 전이 서비스가 분리되어 단순한 단일 서비스 메서드보다 흐름 추적 비용이 증가합니다.

## 선택의 근거는 어떻게 되나요?

- 외부 네트워크 호출을 트랜잭션 밖으로 분리해 DB 커넥션·잠금 장기 점유를 방지합니다.
- `CONFIRMING` 선점과 `@Version`은 동시 요청 중 하나만 승인 권한을 확보하도록 합니다.
- Toss 승인 요청에 Payment별 승인 멱등 키를 사용해, 복구 또는 재시도 상황에서 PG의 중복 승인을 줄입니다.
- 응답 유실을 즉시 `FAILED`로 처리하지 않고 PG 상태를 다시 조회하므로, 실제 승인된 결제를 실패로 잘못 전이하는 일을 방지합니다.
- 최종 상태 전이 시 Payment Status Outbox를 함께 저장해 Order 상태 통지까지 연결합니다.

## 선택지의 한계는 무엇인가요?

- PG 승인 성공 직후 애플리케이션이 종료되면 Payment는 한동안 `CONFIRMING`으로 남고 복구 배치가 필요합니다.
- 복구 주기와 최대 CONFIRMING 시간만큼 최종 상태 확정이 지연될 수 있습니다.
- 낙관적 락 충돌은 두 번째 요청을 즉시 성공 응답으로 만들지 않고 진행 중 예외로 반환합니다.
- PG 상태 조회도 장애가 날 수 있으므로 복구 배치는 다음 주기에 다시 시도합니다.

## 다른 선택지는 무엇이 있었나요?

- 기타 선택지 1 : DB 트랜잭션 안에서 Toss 승인 API를 호출합니다.
  - 구현은 단순하지만 외부 응답 지연 동안 DB 자원을 점유하고, PG 장애가 핵심 트랜잭션을 불안정하게 만듭니다.
- 기타 선택지 2 : 승인 요청 실패를 모두 즉시 `FAILED`로 전이합니다.
  - 빠르게 종결할 수 있지만, Toss에서 이미 승인된 결제를 실패 처리해 결제 상태 불일치를 만들 수 있습니다.
- 기타 선택지 3 : 비동기 승인 큐를 두고 클라이언트 요청은 항상 접수 응답만 반환합니다.
  - 요청 스레드 점유를 줄일 수 있지만, 현재 사용자 결제 완료 흐름과 API 계약을 크게 바꾸고 운영 구성도 추가됩니다.
