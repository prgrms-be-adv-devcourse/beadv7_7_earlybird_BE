# Payment-Service 기술 의사결정 요약 `#003`

- 날짜 : 2026-08-21

##  무슨 상황 인가요?

- 문제 상황: 결제 상태가 `PAID`, `FAILED`, `CANCELLED`로 전이된 뒤 Order Service에 Kafka 상태 이벤트를 전달해야 합니다.
- 상태 전이 트랜잭션 안에서 Kafka를 직접 발행하면, DB 커밋 실패 후에도 이벤트가 발행되거나 Kafka 장애가 결제·환불 상태 전이 자체를 실패시킬 수 있습니다.
- 반대로 DB 저장만 성공하고 이벤트 발행이 실패하면 Order가 결제 결과를 알 수 없어 상태 정합성이 깨질 수 있습니다.
- 즉시 발행과 스케줄러 재시도가 같은 Outbox를 처리할 수 있으므로, 발행 대상을 원자적으로 선점해야 합니다.

## 무엇을 목표로 하나요?

- 목표 품질 속성 : 정합성, 가용성, 장애 복구성
  - 결제 상태 전이와 발행 대상 기록이 함께 커밋되어야 합니다.
  - Kafka 발행 실패가 결제·환불 상태 전이 트랜잭션을 롤백시키지 않아야 합니다.
  - Kafka가 일시적으로 실패해도 발행 대상이 남아 재시도되어야 합니다.
  - 즉시 발행과 스케줄러, 다중 인스턴스 환경에서 동일 Outbox의 동시 발행을 최소화해야 합니다.

## 무엇을 선택 했나요?

- 결제 상태 전이 트랜잭션 안에서 `PaymentStatusOutbox`를 `PENDING` 상태로 저장합니다.
- 트랜잭션 커밋 후 `@TransactionalEventListener(AFTER_COMMIT)`가 새 트랜잭션에서 즉시 Kafka 발행을 시도합니다.
- 즉시 발행 실패는 로그만 남기고 Outbox를 `PENDING`으로 유지합니다. 스케줄러가 주기적으로 PENDING Outbox를 재시도합니다.
- 발행 전 `PENDING → PROCESSING` 조건부 update로 Outbox를 선점합니다. 이미 다른 실행 주체가 선점한 경우 Kafka를 발행하지 않습니다.
- Kafka 발행 성공 후 `SENT`로 전이합니다. `PROCESSING` 상태가 5분을 초과하면 복구 배치가 다시 `PENDING`으로 변경합니다.

```text
결제 상태 전이 + PENDING Outbox 저장
                |
             DB commit
                |
        AFTER_COMMIT 즉시 발행
                |
  PENDING -- claim --> PROCESSING -- Kafka 성공 --> SENT
                |
             Kafka 실패
                |
             PENDING 유지
                |
        스케줄러 재시도 / 5분 경과 PROCESSING 복구
```

- 희생/비용 :
  - Kafka 발행 성공 후 `SENT` 저장 전에 프로세스가 종료되면 이벤트가 재발행될 수 있습니다.
  - Outbox 테이블, 재시도 스케줄러, PROCESSING 복구 관리가 추가됩니다.
  - 전달 보장은 exactly-once가 아니라 at-least-once입니다.

## 선택의 근거는 어떻게 되나요?

- 상태 전이와 Outbox 저장을 같은 DB 트랜잭션에 묶어 결제 상태만 변경되고 발행 대상이 사라지는 경우를 방지합니다.
- Kafka 발행을 커밋 이후로 미뤄 외부 브로커 장애가 결제·환불 상태 변경을 롤백시키지 않게 합니다.
- 즉시 발행으로 스케줄 주기만큼 상태 통지가 지연되는 문제를 줄이고, 스케줄러 재시도로 일시적 장애를 복구합니다.
- 조건부 update는 조회한 Outbox 객체가 오래됐더라도 DB의 현재 상태를 기준으로 선점하므로 중복 발행 가능성을 줄입니다.
- at-least-once 전달을 전제로 Order Consumer가 이벤트 식별자 또는 `orderId + paymentStatus` 기준으로 멱등 처리하면 최종 정합성을 확보할 수 있습니다.

## 선택지의 한계는 무엇인가요?

- Kafka 발행과 `SENT` 저장은 하나의 원자적 트랜잭션이 아니므로, 프로세스 장애 시 중복 발행 가능성을 제거할 수 없습니다.
- 소비 측 멱등 처리가 없으면 재발행 이벤트가 Order 상태 전이에 영향을 줄 수 있습니다.
- 단일 인스턴스 운영에서는 동작하지만, 일괄 환불 스케줄러 자체의 다중 인스턴스 작업 선점은 별도 과제입니다.
- Outbox 생성의 `exists → save` 경합은 현재 남아 있으며, 중복 키 예외 처리 정책은 별도 결정이 필요합니다.

## 다른 선택지는 무엇이 있었나요?

- 기타 선택지 1 : 결제 상태 전이 트랜잭션에서 Kafka를 직접 발행합니다.
  - 구현은 단순하지만 DB 커밋과 Kafka 발행의 원자성을 보장할 수 없고, Kafka 장애가 핵심 결제 트랜잭션을 실패시킬 수 있습니다.
- 기타 선택지 2 : 스케줄러만 사용하고 즉시 발행하지 않습니다.
  - 구현과 부하 제어는 단순하지만, 정상 상황에서도 상태 통지가 스케줄 주기만큼 지연됩니다.
- 기타 선택지 3 : 분산 트랜잭션으로 DB와 Kafka를 함께 커밋합니다.
  - 중복 발행 문제를 줄일 수 있지만 운영 복잡도와 결합도가 커져 현재 서비스 범위에는 과합니다.
