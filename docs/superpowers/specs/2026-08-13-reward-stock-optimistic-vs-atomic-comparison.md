## 1. 개요 및 배경 (Background)

### 1.1 도메인 및 아키텍처 환경

* **시스템 구조:** MSA(Microservices Architecture) 환경
* **대상 서비스:** `Project Service` (재고/리워드 관리) 및 `Order Service` (주문/결제 처리)
* **주요 기능:** 수량형 리워드(동일 자원에 N개의 수량 존재)에 대한 **선착순 동시 차감(Decrease)** 및 결제 실패 시 **보상 트랜잭션 기반 재고 복구(Restore)**

### 1.2 발생한 문제 상황 (Problem Statement)

* **네트워크 타임아웃 및 이중 요청:** `Order Service`가 `Project Service`로 재고 차감 요청을 보냈으나 네트워크 응답 지연으로 인해 재시도(Retry) 요청이 접수될 위험 존재.
* **분산 환경의 일관성 깨짐:** 서비스 간 DB가 분리되어 있어 단일 DB 트랜잭션으로 주문-재고-결제를 묶을 수 없음.
* **고동시성 재고 경합 성능 저하:** 기존 `develop` 브랜치의 **낙관적 락(`@Version` + `@Retryable`)** 방식 적용 시, 동시 요청 폭주 상황에서 **재고가 남아있음에도 구매 실패가 발생**하고 **응답 지연시간(Tail Latency)이 극단적으로 증가**하는 현상 발견.

## 2. 해결 과제 및 아키텍처 패턴 적용 (Solutions)

### 2.1 멱등성(Idempotency) 보장

* 요청마다 유일한 멱등키(Idempotency Key, `orderId`+`rewardId`+`operation`)를 생성하여 전달.
* 동일한 멱등키 요청이 재접수되면 **최초 1회만 실제 DB 차감을 실행**하고, 이후 동일 요청에 대해서는 차감 동작 없이 **성공 응답(`HTTP 200 OK`)만 반환**하여 이중 차감 방지.

### 2.2 Saga 패턴을 이용한 최종 일관성(Eventual Consistency) 보장

* 2PC(Two-Phase Commit) 대신 **Saga 패턴 기반의 보상 트랜잭션(Compensating Transaction)** 구축.
* 결제 단계 실패 시, `Project Service`로 재고 복구(`Restore`) 이벤트를 발행하여 최종적 데이터 일관성 달성.

## 3. 동시성 제어 전략 기술 비교 (Deep Dive)

동시성 충돌을 해결하기 위한 3가지 대표 기법을 고동시성 수량형 재고 차감 관점에서 비교 검토했다. **이 중 실제로 이 저장소에 구현하고 4장의 k6 부하테스트로 실측한 것은 낙관적 락(develop)과 원자적 업데이트 두 가지뿐이다.** 비관적 락은 일반적으로 알려진 특성에 근거한 이론적 검토이며, 이 프로젝트에서 구현·측정하지 않았다.

### 3.1 낙관적 락 (Optimistic Locking) — 실측함

* **동작 원리:** DB 락을 잡지 않고 `SELECT` 시점의 `@Version` 컬럼 값을 유지한 뒤, `UPDATE` 시점에 `WHERE version = :version` 조건으로 변경 여부 검증. 충돌 발생 시 예외(`ObjectOptimisticLockingFailureException`) 발생 ➔ 애플리케이션의 `@Retryable` 루프를 통해 재시도.
* **장점:** DB Row Lock을 잡지 않아 단순 조회 읽기 부하가 적음, 데드락 발생 위험 없음.
* **치명적 단점:**
  1. **가짜 실패(Lock Conflict) 발생:** 재고가 남아있어도, 설정된 재시도 횟수(`maxAttempts = 3`) 동안 계속해서 쓰기 경합에서 밀리면 **재고가 남아있음에도 구매가 거부됨**.
  2. **서버 자원 소모:** 충돌이 빈번할수록 백오프 대기 시간(`delay = 50ms`)과 연쇄 재시도가 누적되어 CPU 및 응답시간 부담 증가.

### 3.2 비관적 락 (Pessimistic Locking) — **이론적 검토, 미실측**

* **동작 원리:** `SELECT ... FOR UPDATE` 구문을 통해 데이터를 읽는 시점부터 DB Row Lock(X-Lock)을 점유.
* **장점:** 데이터 일관성이 100% 보장되며, 락을 획득하면 복잡한 애플리케이션 `if/else` 비즈니스 로직을 안전하게 수행 가능.
* **치명적 단점(일반론):**
  1. **단일 행 락 경합(Single Row Lock Contention):** 수량이 몇 개든 DB 입장에서는 단 1개의 Row에 락이 걸리므로, 재고가 충분해도 사용자들이 줄을 서서 대기(Wait)해야 함.
  2. **DB Connection Pool 고갈:** External API(PG 결제 등)나 네트워크 통신 시간이 트랜잭션에 포함될 경우 DB 커넥션이 오랫동안 반납되지 않아 전체 시스템 마비 위험.
* **주의:** 위 장단점은 일반적으로 알려진 특성이며, 이 저장소에서 구현하거나 k6로 실측한 결과가 아니다. 필요하면 별도 브랜치로 구현 후 4장과 동일한 조건으로 재측정해야 한다.

### 3.3 원자적 업데이트 (Atomic Update) — 실측함, **최종 선택**

* **동작 원리:** DB 엔진 고유의 원자적 연산 기능을 활용하여 조건 검증과 수량 차감을 단 1줄의 SQL로 실행.

  ```sql
  UPDATE reward
     SET remaining_quantity = remaining_quantity - :quantity
   WHERE id = :rewardId AND remaining_quantity >= :quantity;
  ```

* **장점:**
  1. **마이크로초(µs) 단위 락 점유:** 단일 쿼리가 실행되는 극도로 짧은 순간에만 DB 락을 점유하고 풀어버리므로 처리량이 높음.
  2. **가짜 실패 100% 제거:** DB 레벨에서 `remaining_quantity >= quantity` 조건을 충족하는지 여부만 판가름하므로, 재시도 루프 자체가 없어 락 타이밍으로 인한 억울한 실패가 발생하지 않음.
  3. **재시도 로직 불필요:** 애플리케이션 레벨의 `@Retryable` 복잡성 제거.
* **단점 및 보완책:**
  * *실패 사유 추적의 어려움:* Affected Rows가 `0`일 때 '재고 부족'인지 '판매 종료'인지 알 수 없음 ➔ **[보완]** Affected Rows가 0인 실패 케이스에 대해서만 PK 기반 재조회를 수행하여 명확한 에러 메시지 생성. (4.3②에서 이 추가 왕복의 실제 비용을 실측했다 — 결과는 방향이 엇갈렸다.)

### 4.3 정교한 지연시간(Latency) 원인 분석 (Deep Analysis)

#### ① "가짜 실패(Lock Conflict)"의 실체와 원인

`develop` 브랜치의 코드 분석 결과, 실패 경로는 두 가지로 명확히 구분된다 (`RewardServiceImpl.java`, `Reward.java`):

1. **진짜 실패:** Domain 내부 `remainingQuantity < quantity` 검증 ➔ "재고 부족" (진짜 품절). DB에 쓰기 시도조차 하지 않는다 — 엔티티가 변경되지 않으므로 Hibernate가 flush할 것이 없다.
2. **가짜 실패:** `@Retryable(maxAttempts = 3, backoff delay = 50ms)` 안에서 3회 연속 `@Version` 쓰기 경합에 패배 ➔ `ConcurrentUpdateFailedException` 발생 (락 충돌). 재고 상태와 무관하게, 순전히 타이밍 때문에 실패한다.

실측 지표에 따르면 decrease 기준 **`lock_conflict` 요청의 p(95) 지연시간은 554.91ms**로, 진짜 품절 응답(280.96ms)의 **약 2배**입니다(554.91 ÷ 280.96 ≈ 1.98배). 이는 50ms의 백오프(Backoff) 대기를 두고 최대 3번 재시도를 반복하다 튕겨 나가기 때문이다.

#### ② "UPDATE + SELECT" 2회 DB 왕복에 대한 검증 — 방향이 엇갈린 결과

이론적으로는 원자적 UPDATE 실패 시 에러 사유 확인을 위한 PK 재조회(`UPDATE` 실패 ➔ `SELECT`)가 낙관적 락의 단일 조회보다 무거워야 한다. 실측 결과는 **일관되지 않았다**:

* **decrease**: 원자적 UPDATE의 진짜 실패 p(95)가 **197.47ms로 낙관적 락(280.96ms)보다 오히려 빠름**.
* **restore**: 반대로 원자적 UPDATE의 진짜 실패 p(95)가 **218.91ms로 낙관적 락(199.32ms)보다 느림** (가설과 같은 방향이지만 차이는 ~20ms, ~10%).

**해석**: DB PK 인덱스를 통한 단건 `SELECT`는 버퍼 풀 메모리 레벨에서 1ms 미만으로 처리되는 반면, Spring/Tomcat/HTTP 요청 처리의 기본 오버헤드는 100ms 이상이다. 따라서 추가 DB 왕복 1회의 이론적 비용은 이 정도 규모의 요청 지연시간 안에서 뚜렷한 신호로 드러나지 않고, decrease/restore의 결과가 서로 반대 방향으로 나온 것도 이 때문으로 보인다. 즉 **"UPDATE+재조회 2왕복이 항상 더 무겁다"는 가설은 이번 실측으로는 확인도 반증도 되지 않았다** — 있어도 노이즈와 구분하기 어려운 수준의 차이다.

#### ③ 원자적 UPDATE의 최종 성능 우위 본질

원자적 UPDATE의 성능상 우위는 "진짜 실패 처리가 항상 더 빠르기 때문"이 아니다(②에서 보였듯 방향이 엇갈린다). 우위의 실질적 근거는 **`maxAttempts = 3`, `backoff = 50ms` 재시도 연쇄로 인해 p(95) 지연시간을 411~555ms까지 끌어올리던 '가짜 실패(Lock Conflict)'라는 최악의 지연 경로(Worst-case Tail Latency) 자체를 구조적으로 없앴다는 데 있다.**

### 4.4 테스트 방법론의 한계

* **단발 실행(single run):** 4.2의 모든 수치는 각 조건당 **1회 실행** 결과다. 반복 측정·평균 없이 단일 실행값을 비교했다. 4.3②에서 decrease/restore의 진짜 실패 지연시간 방향이 정반대로 나온 것 자체가, 이 규모의 차이(10~20% 이내)는 반복 실행 없이는 실제 구조적 차이인지 런투런 변동(노이즈)인지 구분하기 어렵다는 것을 보여준다.
* **단일 로컬 MySQL 인스턴스 공유:** 같은 컨테이너를 9개 서비스 스키마가 공유한다(`docs/1_LOCAL_DB_SETUP.md`). 테스트 시점에 다른 서비스가 유휴 상태였다고 가정했을 뿐 별도로 격리 검증하지는 않았다.
* **비관적 락 미비교:** 3.2에서 언급했듯 이 문서의 실측 비교는 낙관적 락 vs 원자적 UPDATE 2개 전략에 한정된다.
* 신뢰도를 높이려면 조건당 3~5회 반복 실행 후 중앙값/분산을 비교하고, 락 대기 타임아웃 근처까지 VUS를 올린 극단 시나리오도 추가로 측정하는 것을 권장한다.

## 5. 결론 및 요약 (Conclusion)

1. **소거법에 의한 선택:**
   * **낙관적 락:** 고동시성 상황에서 재시도 폭주로 인한 가짜 실패(decrease 52건·restore 37건) 유발이 실측으로 확인되어 탈락.
   * **비관적 락:** 수량형 재고 구조에서 단일 Row Lock 대기로 인한 병목 및 DB 커넥션 고갈 위험이 있다는 일반론에 근거해 배제 — **이 저장소에서 구현·실측하지는 않았다.**
   * **원자적 업데이트:** 실측 결과, 가짜 실패를 구조적으로 제거하고 decrease 성공 요청 평균 응답시간을 14.1% 단축시켜 **최선의 선택**으로 확정.

2. **최종 정합성 및 성능 성과:**
   * **100% 정합성 검증:** 300개 수량 차감 및 복구 테스트에서 단 1개의 오차도 없이 정합성 달성 (두 브랜치 모두).
   * **가짜 실패 0건 달성:** 락 경합 패배로 인한 고객 구매 실패 케이스 완전 소멸 (decrease 52건 ➔ 0건, restore 37건 ➔ 0건).
   * **사용자 응답 속도 향상:** decrease 성공 요청의 평균 응답 속도 **14.1% 개선** (323.84ms ➔ 278.01ms).
   * **단, 진짜 실패(품절) 처리 자체가 원자적 UPDATE에서 항상 더 빠르다고는 결론지을 수 없다** — decrease/restore 결과가 엇갈렸고, 이는 4.4의 방법론 한계(단발 실행) 안에서 해석해야 한다.
   * **MSA 환경 안정성 확보:** Saga 보상 트랜잭션과 멱등키 메커니즘을 결합하여 원자적 UPDATE의 분산 환경 한계점을 보완했다.
